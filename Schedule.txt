## 4. Rules for every working day

Follow this routine regardless of which day you are on.

First 10–20 minutes: Understand

Read the day's task. Write down what you think you need to do and why.

Next 40–120 minutes: Implement

Write and run the code yourself in small steps. Inspect outputs after each major step instead of running a large block blindly.

Last 10–20 minutes: Explain and record

Write what you learned, what went wrong, and what the output means. Update `project_log.md`.

These are flexible blocks, not strict limits. A one-hour session is enough to make meaningful progress; use up to three hours when a task genuinely needs it. If you get stuck, spend some time understanding the error rather than copying a fix you cannot explain.

# 5. Complete 40-day schedule

## Week 1 — Project setup and data understanding

Goal: Set up the project and understand exactly what you are trying to predict.

Deliverable by the end of the week: working project workspace, dataset files, and a clear problem statement.

### Day 1: Set up the project workspace

1–2 hours

1. Create AI-Learning-Companion in Google Drive.
2. Create data/raw, data/processed, notebooks, and reports folders.
3. Create project_log.md and notebooks/01_problem_and_data.ipynb.
4. Write a first draft of the problem statement, objective, and expected outcome.
5. Record your starting knowledge and today's questions.

End-of-day output: Folder structure, first notebook, project log.

### Day 2: Download and organize the dataset

1–2 hours

1. Open the Kaggle competition page and review its rules and data description.
2. Download the available training, test, and sample-submission files, if provided.
3. Place the original files in data/raw without editing them.
4. Record each filename, file size, source link, and any license or usage restrictions.
5. If access or download fails, resolve that before moving on.

End-of-day output: Original dataset stored and documented.

### Day 3: Load the data in Colab

1–2 hours

1. Mount Google Drive in Colab.
2. Read the training CSV using pandas; locate the file from your Drive folder.
3. Inspect the first five and last five rows.
4. Check shape, column names, data types, and the target column.
5. Read any provided data dictionary or competition instructions.

End-of-day output: Notebook can load the dataset and describe its schema.

### Day 4: Understand the columns

1–2 hours

1. Classify each column as numeric, categorical, date/identifier, target, or uncertain.
2. Check unique values in categorical columns and sensible ranges for numeric columns.
3. Investigate the meaning and units of the target and each promising feature.
4. Identify identifiers and possible features that reveal the target indirectly.
5. Write down questions rather than guessing at unclear columns.

End-of-day output: Column-description table and initial feature list.

### Day 5: Check data quality and define the problem

1–2 hours

1. Count missing values and duplicate rows.
2. Check impossible values, unusual ranges, and unexpected data types.
3. Confirm whether the target is available in training data and absent from test data.
4. Write the problem statement, target, candidate inputs, evaluation plan, and limitations.
5. Commit a short Week 1 summary in reports or the notebook.

End-of-day output: Data-quality summary and a finalized V1 problem definition.

### Day 6: Catch up and explain your data

1 hour

1. Review anything unfinished from Days 1–5.
2. Without looking at your notes, explain what each important column represents.
3. Re-run the notebook from top to bottom and fix any broken cells.
4. List three assumptions you still need to verify.

End-of-day output: A reproducible first notebook.

### Day 7: Rest or light review

Optional, 1 hour

1. Take a break or review the Week 1 summary.
2. Write three questions you can now answer and three you still cannot.
3. Do not begin advanced modeling just to get ahead.

End-of-day output: A short reflection, if you choose to work.

## Week 2 — Exploratory Data Analysis (EDA)

Goal: Understand the patterns, distributions, relationships, and limitations in the data before training models.

Notebook: `02_eda.ipynb` · Deliverable: charts and written observations.

### Day 8: Create the EDA notebook

1–3 hours

1. Create 02_eda.ipynb and load the training data.
2. Review the data types and missing-value counts again.
3. Separate the target from input features conceptually; don't delete columns without a reason.
4. Create a short markdown section stating what each analysis should answer.

Output: Organized EDA notebook.

### Day 9: Explore the target variable

1–3 hours

1. Calculate the target's count, mean, median, standard deviation, minimum, and maximum.
2. Plot a histogram and, where useful, a box plot of the target.
3. Look for skew, outliers, and unusual concentration of scores.
4. Write what these patterns imply for a regression problem.

Output: Target-distribution charts and observations.

### Day 10: Explore individual features

1–3 hours

1. Separate numeric and categorical features.
2. Use descriptive statistics for numeric columns.
3. Inspect category counts for categorical features.
4. Plot suitable histograms or bar charts for a useful selection of features.
5. Investigate suspicious values rather than automatically removing them.

Output: Feature-distribution charts.

### Day 11: Study relationships between features and target

1–3 hours

1. Compare numeric features with the target using scatter plots or grouped summaries.
2. Use correlation for appropriate numeric variables, remembering that correlation does not prove causation.
3. For categorical variables, compare target distributions across groups.
4. Identify promising features and possible redundant features.

Output: Relationship charts and a preliminary feature shortlist.

### Day 12: Check outliers, leakage, and data quality

1–3 hours

1. Revisit unusual observations found in the charts.
2. Check whether any feature is recorded after the outcome or directly calculates the target.
3. Investigate duplicate records and potential repeated individuals or groups, if relevant.
4. Decide which issues require action and document why.

Output: A documented plan for data-quality handling and leakage prevention.

### Day 13: Summarize EDA findings

1–3 hours

1. Write five to ten evidence-based observations from your analysis.
2. Choose a small set of charts that clearly communicate the important patterns.
3. Record limitations, possible biases, and questions that the dataset cannot answer.
4. Do not claim a feature causes productivity to increase just because it correlates with the target.

Output: EDA summary in reports/ or the notebook.

### Day 14: Review and catch up

1–3 hours

1. Restart and run 02_eda.ipynb from top to bottom.
2. Fix inconsistent chart labels, unclear headings, or code that depends on hidden state.
3. Explain each chart in plain language without reading the code.
4. List the preprocessing decisions you will test next week.

Output: Clean, understandable EDA notebook.

## Week 3 — Preprocessing and a reliable validation strategy

Goal: Prepare features correctly and create a fair way to compare models.

Notebook: `03_preprocessing.ipynb` · Deliverable: a reproducible preprocessing workflow.

### Day 15: Separate target and input features

1–3 hours

1. Define X as the selected input features and y as the target.
2. Exclude the target, identifiers that should not predict the outcome, and any confirmed leakage columns from X.
3. Inspect X and y shapes and confirm they align.
4. Record why each excluded column was excluded.

Output: Clear X/y separation and documented feature decisions.

### Day 16: Create train and validation sets

1–3 hours

1. Split the labeled training data into training and validation sets, for example 80/20.
2. Set random_state so the split can be reproduced.
3. Use a suitable split strategy if the data contains time ordering, repeated people, or related groups.
4. Keep the validation set out of all fitting and tuning decisions except evaluation.

Output: A reproducible split with no accidental target leakage.

### Day 17: Build numeric and categorical preprocessing

1–3 hours

1. Identify numeric and categorical input columns from their actual data types and meaning.
2. Plan missing-value handling using SimpleImputer.
3. Plan scaling for numeric features when useful and one-hot encoding for nominal categories.
4. Use ColumnTransformer to apply the right steps to the right columns.
5. Don't manually fit transformations on the entire dataset before splitting.

Output: Preprocessing plan based on actual column types.

### Day 18: Build a preprocessing pipeline

1–3 hours

1. Create a scikit-learn Pipeline containing preprocessing and a simple model placeholder or baseline model.
2. Fit preprocessing only through the training pipeline.
3. Transform the validation set using the already-fitted pipeline.
4. Check that transformed data has the expected dimensions and contains no unexpected missing values.

Output: Reusable pipeline without preprocessing leakage.

### Day 19: Test and document the pipeline

1–3 hours

1. Test the pipeline on a small run of training and validation data.
2. Handle any errors involving column types, missing values, or unknown categories.
3. Confirm that validation rows were not used to fit preprocessing.
4. Save the working code in 03_preprocessing.ipynb and document important choices.

Output: Working preprocessing pipeline and clear notes.

### Day 20: Review your evaluation strategy

1–3 hours

1. Review why a validation set is needed when test labels are unavailable.
2. Learn the definitions and interpretation of MAE, RMSE, and R².
3. Decide which metric is primary and why; MAE is often easier to interpret in target-score units.
4. Check whether the split and metrics match the data and competition rules.

Output: Evaluation plan ready before model comparison.

### Day 21: Catch up and explain the pipeline

1–3 hours

1. Run 03_preprocessing.ipynb from top to bottom.
2. Explain fit versus transform and why splitting comes before fitting transformations.
3. Explain how your pipeline handles missing numeric and categorical values.
4. Fix the notebook or postpone the next phase if the pipeline is not reliable.

Output: Reproducible preprocessing and a written explanation.

### What you must understand before moving on

- A model can produce predictions without being useful.
- A more complicated model is not automatically better.
- Lower MAE and RMSE generally mean smaller prediction errors on the same target and evaluation set.
- R² measures performance relative to a mean-prediction reference; it can be negative on validation data.
- You must compare models on the same validation split using the same metrics.

### A critical rule about validation

Use your training data for model fitting and cross-validation. Keep the held-out validation set for assessing the model-selection decisions you make. If you repeatedly change the model based on validation results, those results become less independent.

The competition's separate test data generally does not include labels, so you cannot calculate its true MAE, RMSE, or R² unless those labels are provided separately.

## 8. What comes after Version 1?

Once the public-dataset model is complete, move to the personal-learning component of the AI Learning Companion. Do not mix your own learning records into the first model unless you have a clear reason and a compatible target.

A sensible Version 2 progression is:

1. Build a learning tracker: record the date, topic, planned task, focused minutes, completion status, difficulty, and next step.
2. Collect your own data consistently: keep tracking for several weeks before attempting personalized prediction.
3. Analyze your habits: examine study frequency, session length, missed sessions, and task completion. Start with descriptive statistics and visualizations.
4. Define one prediction target: for example, estimate how long a particular type of task might take, once you have enough relevant historical examples.
5. Evaluate it honestly: compare against a simple baseline. If your personal dataset is too small, keep the feature as tracking or a rule-based insight rather than claiming an ML model is accurate.
6. Build a simple interface: only after the tracking and modeling logic work reliably, consider a lightweight dashboard for daily use.

The key is to finish one sound project rather than rush into many algorithms or features.

Your first action: Begin with Day 1. Create the project folder and `project_log.md`, then open `01_problem_and_data.ipynb` in Google Colab. Do not start model training yet. The first milestone is to understand the data and define the problem clearly.
